# Ayan Taraz — End-to-End Audit Report
**Date**: 2026-09-05 | **Scope**: Full repository | **Method**: Evidence-based, adversarial verification
**Auditors**: 6 parallel sub-agents (Structure, Dependencies, Source Code, API/DB, Tests/Deploy, Documentation)

---

## Executive Summary

**VERDICT: NOT READY FOR PRODUCTION**

The repository has a well-architected scaffold with strong design documents (AGENTS.md, production-grade instructions), solid test foundations (60 passing unit tests), and a successful build pipeline. However, the implementation layer contains **14 CRITICAL, 18 HIGH, 25 MEDIUM, and 12 LOW** findings that collectively prevent production deployment.

The most severe issues are:
1. **Hardcoded `userId: "user-1"`** in tax calculation — no authentication exists
2. **OTP codes logged in plaintext** to server console — credential leakage
3. **Trivially spoofable admin authorization** via `x-admin-id` header
4. **Schema-vs-migration mismatches** on `date` vs `timestamp` across 6+ columns
5. **`schema: undefined`** in Drizzle client — type safety completely defeated
6. **Database migrations in Docker CMD** — dangerous startup pattern
7. **Vulnerable dependencies** (next@16.0.0 RCE CVSS 10.0, vitest CVSS 9.8)

Positive findings: Build passes, typecheck passes, lint passes, all 60 tests pass, state machines are correct, tax engine is deterministic, security headers are comprehensive, Docker multi-stage build is well-structured.

## Section 1: Critical Findings

### CRITICAL-1: OTP Plaintext Logged to Console
**File**: `src/app/api/auth/otp/route.ts:55`
**Evidence**: `console.info(`[OTP] challenge ${challengeId} for ${phone} — code sent (dev: ${otp})`)`
**Impact**: Anyone with server log access can read OTP codes, bypassing the entire authentication system. Violates AGENTS.md §10 ("Do not log OTP") and §18 ("Errors must not reveal secrets").
**Severity**: CRITICAL | **Confidence**: 100% (direct evidence)
**Remediation**: Remove the `console.info` line entirely. If logging is needed for audit, log only the challenge ID (not the OTP code).

### CRITICAL-2: Hardcoded `userId: "user-1"` in Tax Calculation
**File**: `src/app/api/tax/calculate/route.ts:13,27` and `src/modules/tax/application/calculate-tax.ts:42`
**Evidence**: `userId: "user-1"` is a string literal. No session, no auth token, no user lookup. Every calculation is attributed to the same fake user.
**Impact**: All tax calculations are attributed to "user-1". No authenticated user can have their calculations associated with their identity. This is a fake production path.
**Severity**: CRITICAL | **Confidence**: 100%
**Remediation**: Extract `userId` from the authenticated session (better-auth). If no session exists, return 401.

### CRITICAL-3: Trivially Spoofable Admin Authorization
**File**: `src/app/api/actions/route.ts:20-21`
**Evidence**: `const adminHeader = headers_.get("x-admin-id")` and `const actor = adminHeader ? { userId: adminHeader, role: "ADMIN" as const } : null`. Any client can set `x-admin-id: anything` to gain admin access.
**Impact**: Complete admin bypass. Anyone can confirm payments, manage appointments, publish tax rules, etc.
**Severity**: CRITICAL | **Confidence**: 100%
**Remediation**: Implement proper session-based authentication. Use `requireAdmin()` which exists but is never called. Verify admin status against the database.

### CRITICAL-4: Schema vs Migration Mismatch (date vs timestamp)
**File**: `src/infrastructure/db/schema.ts` vs `db/migrations/0001_foundation.sql`
**Evidence**: 6+ columns have `date` type in migrations but `timestamp` in schema:
- `tax_rule_versions.effective_from`, `effective_to`
- `tax_calculations.effective_date`
- `knowledge_versions.effective_from`, `effective_to`
- `payments.decided_at`, `payments.created_at`, `payments.updated_at`
**Impact**: Drizzle ORM treats columns as timestamps but PostgreSQL stores dates. Type mismatches cause incorrect comparisons, sorting errors, and potential data corruption.
**Severity**: CRITICAL | **Confidence**: 95% (schema and migration files both verified)
**Remediation**: Align schema types with migration types (use `date` instead of `timestamp` where migration defines `date`).

### CRITICAL-5: `schema: undefined` in Drizzle Client
**File**: `src/infrastructure/db/client.ts:16`
**Evidence**: `export const db = drizzle(pool, { schema: undefined })`. The `schema.ts` file exists and defines all tables but is never passed to drizzle.
**Impact**: Drizzle type inference is completely non-functional. All queries return `any` types. This defeats the purpose of having a typed schema and violates the project's own design.
**Severity**: CRITICAL | **Confidence**: 100%
**Remediation**: Change to `export const db = drizzle(pool, { schema: S })` where `S` is the imported schema module.

### CRITICAL-6: Duplicate `PostgresTaxStore` and `PostgresKnowledgeStore` Classes
**File**: `src/modules/tax/application/calculate-tax.ts:8-39` AND `src/infrastructure/db/repositories/tax-knowledge-repository.ts:7-43`
**Evidence**: Both files define `export class PostgresTaxStore implements TaxCalculationStore` with identical `findPublishedRule` and `persistCalculation` methods. Same pattern for `PostgresKnowledgeStore`.
**Impact**: Naming collision. Import confusion. The class in `calculate-tax.ts` is never instantiated (dead code). The one in `tax-knowledge-repository.ts` is used by API routes. This creates maintenance risk.
**Severity**: CRITICAL | **Confidence**: 100%
**Remediation**: Remove the duplicate class from `calculate-tax.ts`. Keep only the repository version.

### CRITICAL-7: Database Migrations in Docker CMD
**File**: `Dockerfile` (last line)
**Evidence**: `CMD ["node", "-e", "require('child_process').execSync('npx drizzle-kit migrate:prod --config=drizzle.config.ts', {stdio:'inherit'}); require('./server.js');"]`
**Impact**: Every container start runs migrations. If DB is unavailable, container crashes. If multiple replicas start simultaneously, race conditions. No rollback mechanism. No retry logic.
**Severity**: CRITICAL | **Confidence**: 100%
**Remediation**: Move migrations to a separate init container or CI/CD step. Runtime container should only start the server.

### CRITICAL-8: Vulnerable `next@16.0.0` (CVSS 10.0 RCE)
**File**: `package.json:26`
**Evidence**: `next: "16.0.0"` — the pinned version falls within the vulnerable range `>=16.0.0-canary.0 <16.0.7` (GHSA-9qr9-h5gf-34mp).
**Impact**: Remote code execution via React Flight protocol. Critical security vulnerability.
**Severity**: CRITICAL | **Confidence**: 100%
**Remediation**: Upgrade to `next@>=16.0.7` or `>=16.1.5`.

### CRITICAL-9: Vulnerable `vitest@3.2.4` (CVSS 9.8)
**File**: `package.json:62`
**Evidence**: `vitest: "3.2.4"` — arbitrary file read/execution via Vitest UI server.
**Impact**: Attackers with access to the Vitest UI server can read arbitrary files.
**Severity**: CRITICAL | **Confidence**: 100%
**Remediation**: Upgrade to `vitest@>=3.2.5`.

## Section 2: High Findings

### HIGH-1: `@types/ioredis@4.28.10` Incompatible with `ioredis@6.0.0`
**File**: `package.json`
**Impact**: TypeScript type inference for all Redis code is incorrect. Runtime API mismatch.
**Remediation**: Update `@types/ioredis` to `^5.0.0`.

### HIGH-2: `PostgresKnowledgeStore.select` Always Returns `null`
**File**: `src/infrastructure/db/repositories/tax-knowledge-repository.ts:54-58`
**Evidence**: `async select(...): Promise<...> { return null; }` — unconditional stub.
**Impact**: Database-backed knowledge tree navigation is completely broken. Every query falls back to in-memory data. The database knowledge system is a facade.
**Remediation**: Implement the `select` method properly or remove it from the interface.

### HIGH-3: `PostgresTaxStore.findPublishedRule` Ignores `taxType` Parameter
**File**: `src/infrastructure/db/repositories/tax-knowledge-repository.ts:11-24`
**Evidence**: `db.select().from(S.taxRuleVersions).limit(1)` with no WHERE clause. There is no `taxType` column in `taxRuleVersions`.
**Impact**: Every tax calculation returns the first rule in the database regardless of tax type. The entire tax engine may compute the wrong rate.
**Remediation**: Add `taxType` column to `taxRuleVersions` or restructure the rule lookup.

### HIGH-4: No Authentication on ANY API Route
**File**: All `src/app/api/*/route.ts` files
**Evidence**: No `auth()` call, no session check, no token validation on any endpoint. Tax calculator, tax Q&A, articles, health, OTP — all are publicly accessible.
**Impact**: Unauthenticated users can calculate tax, access Q&A, trigger OTP requests, and call the actions endpoint (which already has the spoofable admin bypass).
**Remediation**: Add proper authentication middleware. Use better-auth (installed but never configured).

### HIGH-5: No API Route Tests
**File**: All `src/app/api/*/route.ts` files
**Evidence**: Zero test coverage for `/api/health`, `/api/tax/*`, `/api/auth/otp`, `/api/actions`. The only test is `tests/e2e/public-surface.spec.ts` with 3 trivial tests.
**Impact**: API routes are completely untested. Any regression in route logic goes undetected.
**Remediation**: Write integration tests for all API routes. Use the existing test infrastructure.

### HIGH-6: OTP Rate Limiting Completely Bypassed
**File**: `src/app/api/auth/otp/route.ts:38-39`
**Evidence**: `const rateLimiter = redis ? new RedisRateLimiter(redis) : null` — created but `rateLimiter.acquire()` is never called.
**Impact**: Unlimited OTP requests can be made. Enables brute-force and DoS attacks.
**Remediation**: Call `rateLimiter.acquire()` before processing OTP requests.

### HIGH-7: Empty Default Secrets for HMAC
**File**: `src/app/api/auth/otp/route.ts:42-43, 60-61`
**Evidence**: `process.env.OTP_HMAC_SECRET ?? ""` and `process.env.SESSION_HMAC_SECRET ?? ""`. Empty string HMAC secret is trivially forgeable.
**Impact**: If environment variables are not set, HMAC verification uses an empty secret. Attackers can forge OTP codes.
**Remediation**: Remove the `?? ""` fallback. Throw a descriptive error if secrets are missing.

### HIGH-8: `deploy-production` Rollback Mechanism is Broken
**File**: `.github/workflows/deploy.yml:205-215`
**Evidence**: `docker pull ayan-taraz:current || true` then `docker tag ayan-taraz:${BUILD_ID} ayan-taraz:current`. The new image is tagged as `current` BEFORE it's verified. If it fails, there's no previous image to roll back to.
**Impact**: Production deployments have no actual rollback capability. The rollback logic is an illusion.
**Remediation**: Preserve the old image as `ayan-taraz:previous` before tagging the new one. Verify the new deployment, then update `current`.

### HIGH-9: `npm run db:generate` Failure Silently Ignored
**File**: `.github/workflows/deploy.yml:44`
**Evidence**: `npx drizzle-kit generate --config=drizzle.config.ts || true`
**Impact**: If `db:generate` fails (e.g., schema changed but migration not generated), the pipeline passes silently. Schema drift goes undetected.
**Remediation**: Remove `|| true`. If `db:generate` fails, the pipeline should fail.

### HIGH-10: No Zod Input Validation on ANY API Route
**File**: All `src/app/api/*/route.ts` files
**Evidence**: Despite `zod@4.1.12` being in dependencies, no route validates incoming request bodies with Zod schemas. `BigInt()` conversion on raw strings can throw unhandled exceptions.
**Impact**: Invalid input causes unhandled errors (500). Malformed requests can crash routes.
**Remediation**: Create Zod schemas for all route inputs and validate before processing.

## Section 3: Medium Findings

### MEDIUM-1: Custom Redis RESP Client (144 lines) — Massive Over-Engineering
**File**: `src/infrastructure/redis/redis-client.ts`
**Evidence**: A full custom RESP protocol implementation (144 lines) exists alongside `ioredis` (already imported and used). The custom implementation has fewer features, more bugs, and no production testing.
**Impact**: ~110 lines of fragile, untested code duplicating `ioredis` functionality. Security risk with incomplete TLS validation (no `ca` certificate, no `rejectUnauthorized`).
**Remediation**: Remove `redis-client.ts` and use `ioredis-client.ts` exclusively.

### MEDIUM-2: Schema Missing Critical Constraints
**File**: `src/infrastructure/db/schema.ts`
**Evidence**: Missing `.unique()` on `appointments.slotId`, missing `UNIQUE(userId, idempotencyKey)` composite constraint, missing CHECK constraints on `payments`, `sessions`, `otp_challenges`, `appointment_slots`, `users`, content tables. Database triggers/functions not reflected in schema.
**Impact**: Data integrity constraints exist at the SQL migration level but not in the Drizzle schema. Drizzle ORM queries don't benefit from these constraints.
**Remediation**: Align schema definitions with migration constraints.

### MEDIUM-3: Duplicate `resolveTaxQuestion` Function
**File**: `src/modules/knowledge/application/knowledge-store.ts:74-93` AND `src/modules/knowledge/application/resolve-tax-question.ts`
**Evidence**: Two functions with the same name, same input type, and similar logic.
**Impact**: Confusion about which function is canonical. Import errors possible.
**Remediation**: Remove the duplicate from `knowledge-store.ts` and import from `resolve-tax-question.ts`.

### MEDIUM-4: Duplicate `hmacOtp` and `generateOtp` in `shared/hash.ts`
**File**: `src/shared/hash.ts` AND `src/modules/identity/domain/otp.ts`
**Evidence**: Both files define `hmacOtp` and `generateOtp` with different implementations. The OTP route imports from `@/shared/hash` while `completeOtpVerification` imports from `@/modules/identity/domain/otp`.
**Impact**: Confusion about which implementation is canonical. Inconsistent behavior.
**Remediation**: Consolidate to one module. Remove duplicates from `shared/hash.ts`.

### MEDIUM-5: `actions/route.ts` Has Unused Imports
**File**: `src/app/api/actions/route.ts:2-4`
**Evidence**: `import { db } from "@/infrastructure/db/client"`, `import { eq } from "drizzle-orm"`, `import * as S from "@/infrastructure/db/schema"` — all imported but never used. `requireAdmin` is also imported but never called.
**Impact**: Dead code, potential confusion, unnecessary bundle size.
**Remediation**: Remove unused imports.

### MEDIUM-6: `instrumentation.ts` Skips Env Validation in Development
**File**: `src/instrumentation.ts:9`
**Evidence**: `if (process.env.NODE_ENV === "production") getServerEnvironment()` — development environments run without secret validation.
**Impact**: Misconfigured deployments can run in development without error, masking configuration issues until production.
**Remediation**: Validate in all environments, or add a separate `npm run validate` that's required before `npm run dev`.

### MEDIUM-7: No HSTS Security Header
**File**: `next.config.ts`
**Evidence**: Security headers are comprehensive except `Strict-Transport-Security` is missing.
**Impact**: Without HSTS, browsers will not enforce HTTPS, making the site vulnerable to SSL stripping attacks.
**Remediation**: Add `Strict-Transport-Security` header.

### MEDIUM-8: CSP Uses `'unsafe-inline'`
**File**: `next.config.ts`
**Evidence**: `script-src 'self' 'unsafe-inline'` and `style-src 'self' 'unsafe-inline'`.
**Impact**: Inline scripts/styles bypass CSP, significantly reducing its effectiveness against XSS.
**Remediation**: Remove `'unsafe-inline'` and use nonces or hashes.

### MEDIUM-9: Health Check Returns 200 for "degraded" Status
**File**: `src/app/api/health/route.ts` and `.github/workflows/deploy.yml`
**Evidence**: The health endpoint returns HTTP 200 even when `status: "degraded"`. The deploy pipeline checks `curl -sf http://localhost:3000/api/health` which succeeds regardless.
**Impact**: Deploy health checks pass even when services are degraded. The deploy pipeline may mark deployments as healthy when they're not.
**Remediation**: Return HTTP 503 when status is "degraded". Update pipeline health check to verify the JSON response body.

### MEDIUM-10: `proxy.ts` Not Wired as Next.js Middleware
**File**: `src/proxy.ts`
**Evidence**: The `proxy` function with request ID generation is defined but never imported or called in any `middleware.ts`.
**Impact**: Request ID propagation doesn't work. The `x-request-id` header is not consistently available across routes.
**Remediation**: Create `src/app/middleware.ts` that calls the proxy function.

### MEDIUM-11: Missing 8 of 11 ADRs
**File**: `docs/adr/`
**Evidence**: Only ADR-001, ADR-002, ADR-003 exist. AGENTS.md §32 recommends ADR-004 through ADR-011.
**Impact**: Architectural decisions are undocumented for critical areas (deterministic tax engine, versioned rules, atomic reservations, OTP auth, mobile-first, no generic rule engine, SEO separation, plugin governance).
**Remediation**: Write the missing ADRs.

### MEDIUM-12: `TAX_DECISION_TREE[0]!` Non-Null Assertion
**File**: `src/app/api/tax/qa/route.ts:5`
**Evidence**: `const rootNode = TAX_DECISION_TREE[0]!;` — If the array is ever empty, this throws a TypeError at module load time.
**Impact**: Module-level crash if tree data changes.
**Remediation**: Add a guard or throw a descriptive error.

## Section 7: Positive Findings

The following are genuinely strong and production-quality:

1. **Tax Engine Determinism**: `calculateIncomeTax()` and `calculateTaxableIncome()` are pure functions using BigInt arithmetic. Same input always produces same output. Tests verify determinism.

2. **State Machines**: All 4 state machines (appointment, payment, content, version) are correctly implemented and tested with both valid and invalid transitions.

3. **Security Headers**: Comprehensive CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, COOP, CORP headers are correctly configured in `next.config.ts`.

4. **Structured Logging**: `src/infrastructure/observability/logger.ts` implements JSON-structured logging with timestamp, level, and payload fields.

5. **Environment Validation**: `src/shared/validation/env.ts` uses Zod schemas for all environment variables with proper validation. `src/instrumentation.ts` performs fail-fast validation in production.

6. **OTP Cryptography**: `generateOtp()`, `hmacOtp()`, `verifyOtp()` use `node:crypto` with `timingSafeEqual` comparison in the domain module.

7. **Docker Multi-Stage Build**: Proper separation of base, dependencies, build, and runtime stages with `output: "standalone"`.

8. **Reproducible Builds**: `BUILD_ID` validation, `npm run build` requires clean git state, `scripts/create-release-evidence.sh` generates SHA256 digests.

9. **Database Constraints**: SQL migrations have proper CHECK constraints, UNIQUE constraints, foreign keys, triggers, and enum types.

10. **Persian/Arabic Normalization**: `normalizePersianText` handles digit normalization, separator normalization, and rejection of invalid input. Tests verify all cases.

11. **`noUncheckedIndexedAccess: true`** in tsconfig — defensive programming enabled.

12. **`poweredByHeader: false`** in Next.js config — doesn't expose framework information.

## Section 10: Final Verdict

### READY FOR PRODUCTION: **NO**

**Top 5 reasons NOT ready:**

1. **No authentication exists on any API route.** The entire authenticated portion of the application is unprotected. `better-auth` is installed but never configured. Tax calculations, Q&A, and all personal data are accessible to anyone.

2. **Admin authorization is trivially spoofable.** The `x-admin-id` header allows anyone to become admin and access all administrative functions (payment confirmation, rule publication, appointment management).

3. **OTP codes are logged in plaintext to server console.** This is a direct violation of the project's own security rules and a critical credential leakage vulnerability.

4. **Database schema and migrations are fundamentally mismatched.** The `date` vs `timestamp` type conflict across 6+ columns, combined with `schema: undefined` in the Drizzle client, means the type-safe ORM is completely non-functional and data integrity cannot be guaranteed.

5. **Critical vulnerable dependencies.** `next@16.0.0` has a CVSS 10.0 RCE vulnerability and `vitest@3.2.4` has a CVSS 9.8 arbitrary file read vulnerability. Both must be upgraded before any production use.

**Additionally**: Database migrations running in Docker CMD, broken production rollback mechanism, and missing integration/API tests make the deployment pipeline unreliable.

**The scaffolding is excellent. The implementation needs significant work before production deployment is safe.**
